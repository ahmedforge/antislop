# Database schema (Stage 4)

PostgreSQL is the source of truth. Alembic owns schema changes; the application
must not call `Base.metadata.create_all()` on startup. Models use SQLAlchemy 2
`Mapped` columns. Migrations are reviewed, explicit operations independent of
future model changes.

## Tables and decisions

| Table | Purpose and constraints |
| --- | --- |
| `channels` | Internal UUID, unique stable YouTube channel ID, optional handle, moderation status, exact decimal score, and timezone-aware timestamps. New channels are `unreviewed`; later stages can move them through `pending_review`, `approved`, or `rejected`. Only `approved` will be blocklisted. |
| `installs` | Client-generated anonymous UUID, nonnegative reputation (default 1), creation time. This is not an account or proof of a unique human; reinstalling can produce another ID. No watch history, IP, or browser fingerprint columns. |
| `reports` | Explicit reason, channel, installation, and creation time. A unique `(install_id, channel_id)` constraint prevents duplicate submissions even under concurrent requests. |
| `appeals` | Channel, optional installation, explicit reason, status (`open`, `accepted`, `rejected`), creation and resolution times. Optional installation leaves room for creator appeals outside the extension. Resolved appeals require a resolution timestamp. |
| `moderation_actions` | Channel, optional appeal, action, admin label, explicit reason, and creation time. Stores audit history, never an admin API key. An appeal action must refer to an appeal for the same channel. |

Internal IDs are UUIDs generated by Python, except installation IDs, which must be
provided by the client. Direct SQL inserts must provide IDs. YouTube IDs must have
`UC` plus 22 permitted characters. Handles are not unique: they can change or be
reassigned; the stable YouTube ID is authoritative. Case-insensitive handle lookup
uses `lower(handle)` and must use the same expression in queries.

Statuses use strings with named database check constraints rather than native
PostgreSQL enums, making future status changes explicit migrations. Scores and
reputation use `numeric(12,4)` rather than floating point, rejecting negative and
nonfinite values. Reasons allow 1–2000 trimmed characters. API-level validation
and authorization arrive in later stages.

Foreign keys use `RESTRICT` so deleting a channel, installation, or appeal cannot
silently erase report or moderation history. This is not an immutable audit log:
the database owner can still change records. Future admin endpoints must treat
moderation actions as append-only and update status plus audit action in one
transaction. No moderation endpoints or scoring logic are implemented yet.

## Indexes

| Index | Why it exists |
| --- | --- |
| Primary keys and unique YouTube ID | Direct identity lookups and database-enforced uniqueness. PostgreSQL creates these indexes automatically. |
| `channels(lower(handle))` | Case-insensitive lookup of reported handles; not a uniqueness assertion. |
| `channels(updated_at, id)` | Ordered delta scans, including channels removed from the approved list. |
| `channels(status, updated_at)` | Review queues and approved-channel scans. |
| Unique `reports(install_id, channel_id)` | Deduplication and reports by an installation; no redundant install-only index. |
| `reports(channel_id, created_at)` | Reports and scoring inputs for a channel in time order. |
| `appeals(status, created_at)` | Oldest open appeals first. |
| `appeals(channel_id)` and `appeals(install_id)` | Channel appeal history and installation references. |
| Unique `appeals(id, channel_id)` | Required target for the composite foreign key validating an action's appeal/channel pair. |
| `moderation_actions(channel_id, created_at)` | Time-ordered moderation history per channel. |
| `moderation_actions(appeal_id)` | Actions associated with an appeal. |

A PostgreSQL trigger refreshes `channels.updated_at` with `clock_timestamp()` on
any insert or update, including raw SQL (insert coverage was added in migration `0002`). Timestamps alone are not a complete synchronization
protocol: the [Stage 5 sync contract](blocklist-sync.md) explains concurrent commits, removal
notifications, and current scale limitations. The timestamp trigger is explicit in the migration and covered by
an integration test; Alembic's model comparison does not inspect trigger bodies.

## Migration workflow

From the repository root, after installing backend dependencies:

```bash
docker compose up -d --wait postgres redis
docker compose build backend
docker compose run --rm --no-deps backend alembic upgrade head
docker compose run --rm --no-deps backend alembic current
docker compose run --rm --no-deps backend alembic check
docker compose up -d --wait backend
```

Expected revision after Stage 5: `0002 (head)`. `alembic check` reports no new upgrade operations.
Migrations are a deliberate deployment step, not run by every API worker.
For local CLI usage, run Alembic from `backend/` with `DATABASE_URL` pointing to
an accessible PostgreSQL server. Compose's database port is intentionally internal.

To develop a new migration from `backend/`:

```bash
.venv/bin/alembic revision --autogenerate -m "describe schema change"
# Review the generated upgrade and downgrade before applying.
.venv/bin/alembic upgrade head
.venv/bin/alembic check
```

`alembic downgrade base` drops all application tables and data. Use it only on a
disposable development/test database. Tests exercise downgrade and re-upgrade
within isolated schemas rather than touching an existing application's tables.

## Integration tests

From `backend/`, supply a PostgreSQL test URL whose role can create schemas:

```bash
TEST_DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:PORT/TEST_DB .venv/bin/python -m pytest -q
```

Each integration test creates a randomly named schema, applies the migration,
checks behavior, then drops only that schema. Without `TEST_DATABASE_URL`, the
health test runs and PostgreSQL tests explicitly skip. The suite checks schema
roundtrips and model drift, defaults, timezone-aware timestamps, direct-SQL update
tracking, duplicates, orphan references, invalid values, and mismatched appeals.
